1Goal

A single app on your private server that shows Chicago, Detroit and Dayton, reachable from anywhere. Dayton reaches Chicago's feature level: the same layers with real Dayton data, popups, filters, focus areas, saved searches, contact list and static mode. Each city is a pack, so a tablet can carry one city (≤ 120 MB) and nothing else. The separate Dayton fork is then archived.

Success means all of the following:

  • ?city=dayton shows no Chicago or Detroit data anywhere.
  • Every Dayton it.todo and skipped pytest is real and passing.
  • VITE_CITIES=dayton npm run build:static produces a bundle with no other city's code or data, at ≤ 120 MB.
  • The server build serves all three cities behind TLS and auth.

3Defects in the fork, and where each is fixed

  1. The transit importer is CTA/Socrata and gets a GTFS zip. → D1: the shared GTFS path, via a gdrta_gtfs_url key.
  2. Federal properties shows Chicago data. → not offered until D8.
  3. The assessor link is Cook County. → D4: the railroadRowPopup/building popup links to mcrealestate.org.
  4. Sanborn shows Chicago sheets centred on the Loop. → D8.
  5. The zoning filter is Chicago's, and the classifier mixes prefixes. → D2 classify_dayton_zone, D5 catalogue.
  6. Railroad filter labels are Chicago's. → D5 taxonomies.
  7. Parks, zip codes and major streets have no importer or table. → D2.
  8. Parcels is a Cook County stub, and the enrichment was never committed. → D2 DaytonParcelsImporter + enrich.py.
  9. Police and neighborhood tables are created by importers rather than migrations. → D2, using tables from migrations 003/005.
  10. start_map.sh points at a missing compose file. → becomes moot after the fork is retired (D9).
  11. About 780 KB of dead Chicago data ships in the fork. → becomes moot after the fork is retired.

A twelfth issue: the fork's ROW buffer is in degrees, so corridors come out about 23% narrower east–west. That is fixed in D2.

4Approach

Merge the fork into the shared app as a city pack. Don't sync two repos. Dayton plugs into the CityProfile / city_registry seam that the Detroit plan defines. Dayton's code is new files; the shared seams each get one registration line. The fork's working Dayton code is ported. Its Chicago-shaped scaffolding is dropped.

Paradigm, mixed by layer:

  • Frontend packs are data-shaped modules plus adapter classes that implement the existing ports.
  • Importers are OOP, as template-method subclasses of BaseImporter.
  • Enrichment and export are procedural, set-based SQL.

The TDD §3 explains why.

Modularity comes at build time: VITE_CITIES drives a Vite plugin that bundles only the chosen profiles and copies only their data folders. Lazy import() keeps unused cities off the network, even in the all-city server build.

Hosting uses the Chicago session's single-server work: a static bundle plus the lookup server behind Caddy, with private access through Tailscale. PostGIS stays a dev-machine import tool.

7.2 Database layout

Kept: one schema, rows keyed by city_id. Per-city schemas or databases would make Martin, routes and migrations city-aware for no gain, since the static artifact is per city anyway. Martin serves all cities' rows in one tile set. That is safe because Chicago, Detroit and Dayton bounding boxes don't overlap. Cincinnati's would nearly touch Dayton's, so it would need Martin function sources filtered by city. That is noted for later.

7.5 Dayton business data

Dayton and Ohio have no free, general business-licence dataset (unverified, but none was found). The options:

  • OSM POIs inside the footprint (chosen; free; lower coverage).
  • Foursquare or Google Places per building. These are paid per call and already wired for phones; use them only on demand.
  • Ohio SOS bulk data. It holds registered-agent addresses, not locations, so it is the wrong signal.

Business discovery stays Chicago-only, and the panel says so.

8Risks

  • Detroit seams slip. D2–D7 block on Detroit P1–P4. Mitigation: start D1 and the D2 importer code now against fixtures, and offer to take Detroit P2 (importers_for) if it stalls, with the Detroit owner's agreement.
  • Upstream drift. City and county ArcGIS layer ids (307, 203, 310, 312) change without notice. Mitigation: verified field maps, recorded fixtures, and an importer warning on unverified maps.
  • Lost enrichment. The fork's 335K enriched buildings exist only in a Docker volume. Mitigation: the D0 pg_dump first.
  • Size budget. Dayton plus Microsoft fallback footprints could exceed 70 MB of buildings. Mitigation: clip to the city limit, and drop tippecanoe attributes not used by the popup.
  • Snapshot branch drift. feat/multi-city-wip froze master's working tree on 2026-10-02, but the other sessions keep editing master. Rebase feat/dayton-skeleton onto the real multi-city commit once it exists. Dayton files are new, so they won't conflict.
