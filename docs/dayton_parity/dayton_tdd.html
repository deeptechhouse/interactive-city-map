1Scope

In scope:

  1. Retire the separate Dayton fork. Dayton becomes a city in the shared interactive-city-map app, through the same CityProfile seam as Detroit.
  2. Bring Dayton to Chicago's feature level in static mode and in dev mode.
  3. Make each city a removable city pack:
    • A server build holds every city and shares resources.
    • A tablet build can hold a single city.

Out of scope: features Chicago itself lacks; Cincinnati, although the seam makes it cheap; interior ML work; Detroit's own parity, which is covered by the Detroit plan.

Constraints:

  • Chicago's and Detroit's output stays identical.
  • Dayton code never imports another city's module.
  • Free, open-source services only, because this is a private project (§2).

2Current state

Dayton exists today as ../Dayton_interactive_map. It is a 12-commit fork of Chicago's March 2026 code. Its core is adapted to Dayton: config, map center, ArcGIS importers, police and neighborhood layers, railroad right-of-way, and an enriched building popup. It has none of Chicago's later work: contacts, saved searches, focus areas, the tools panel, static mode, deployment, and the city-profile seam.

Several layers render empty or show another city's data. Federal properties shows Chicago data, the assessor link points to Cook County, and the zoning and railroad filters use Chicago vocabularies. The transit importer cannot read GTFS, and parcels hits a stub. Estimated parity is ≈35%. The full matrix is in plan §2.

The shared app's own multi-city seam (CityProfile, registry.ts, city_registry.py, export_city_static.py) was designed in the Detroit TDD and is still stubbed and uncommitted on master. This design builds on it and does not redesign it. Interface changes go through the Detroit plan's owner.

3Architecture

A green outline marks a city pack or a new seam. The database is a build-time tool. The deployed artifact is static files plus the small lookup server, so a tablet never needs PostGIS.

Paradigm and design principles

  • Paradigm, mixed by layer (§5):
    • Frontend city packs are data-shaped modules: a profile object, pure functions and adapter classes implementing existing ports. That is the idiom of the React and hooks code.
    • Importers stay OOP, as subclasses of BaseImporter and the shared importers, because the pipeline already uses template-method classes.
    • Enrichment and export are procedural SQL scripts, because set-based SQL is the right tool for spatial joins.
  • Open/Closed: Dayton is added as new files. The two shared seams each need one registration line: registry.ts and CITY_OVERRIDES.
  • Dependency inversion: shared code depends on CityProfile, OwnerSource/BusinessSource and BaseImporter, never on Dayton.
  • Fail closed: an unknown VITE_CITIES slug breaks the build, and an unknown ?city= returns null. Features Dayton doesn't have yet (focus, contacts) are null, so the UI shows a "not available" note instead of another city's data.
  • Single source of truth:
    • Upstream field names live in dayton/field_maps.py.
    • Vocabularies are generated by the exporter: POI counts and GDRTA colours.
    • The layer id list is DAYTON_LAYER_IDS.

4Data model

There are no new tables. Dayton reuses the shared schema: id uuid, city_id → cities.id, SRID 4326, metadata JSONB, a GIST index on geom and a btree index on city_id. The fork created ad-hoc tables (wards, police_districts) with raw SQL. Those are not carried over.

5.3 City switch

Same lifecycle as Detroit TDD §5.3: on a switch, removeCityLayers clears the previous city's layers, the profile's layers are added, and a flyTo moves to its center. Saved searches are already keyed per city. Contact lists are kept per city.

5.4 Focus areas

Dayton reuses the three FocusKind slots: zip = ZCTAs, police = DPD areas, ward = Neighborhoods (97), labelled through kindLabels. Dayton has no wards or council districts, because its City Commission is at-large. Boundaries are loaded with a lazy import() from src/cities/dayton/data/.

5.5 Zoning

DAYTON_ZONE_CLASSES is consumed through buildZoningFilter(classes) (Detroit P5). Its families are unproven until a GROUP BY zone_code runs after import. The keys must equal the backend's zone_class values.

5.6 Contacts

  • Owners: MontgomeryCountyOwnerSource, which queries the county parcels FeatureServer from the browser. CORS is unverified; the fallback is a proxy through the lookup server.
  • Businesses: DaytonPoiBusinessSource, which uses OSM POIs inside the footprint. Dayton has no business-licence dataset, so coverage is lower than Chicago's, and the panel says so.
  • Postal defaults are DAYTON, OH. The corporation link goes to the Ohio Secretary of State.
  • Phone lookups add dayton=google,foursquare to PHONE_LOOKUP_PROVIDERS_BY_CITY.

Fork code to port, not rewrite:

  • arcgis_rest_importer.py: merge any missing behaviour into the shared arcgis_helper. MapServer pagination differs from FeatureServer pagination.
  • import_police_districts.py and import_neighborhoods.py become the boundaries importer.
  • scripts/generate_railroad_row.py becomes the ROW importer.
  • The fork's newer dayton.yaml source URLs replace the shared repo's older copy.

8City packs: modular builds

A city pack has three parts:

  • src/cities/<slug>/: the profile code.
  • src/cities/<slug>/data/: bundled GeoJSON, loaded only with import().
  • public/data/<slug>/: PMTiles.

Assets every pack may use go in public/data/shared/ (and fonts in public/fonts/).

MechanismWhat it removesWhere
VITE_CITIES → parseEnabledCities (fail closed)—src/cities/packs.ts
virtual:city-profiles lists only the enabled profiles; registry.ts reads itOther cities' code from the bundlevite/cityPackPlugin.ts
Filtered public copy (isPathInBuild) instead of Vite's copy-everythingOther cities' PMTiles from distsame plugin, writeBundle
Dynamic import() for each city's bundled GeoJSONUnused data from the first page load, even in an all-city buildeach profile's focus.ts / layers
Prerequisite owned by the Detroit plan, P3/P4:
  • Chicago's static files must move from flat public/data/*.pmtiles to public/data/chicago/.
  • Chicago's static_*.ts GeoJSON (about 4.5 MB, imported eagerly today) must become lazy imports.

Until then, isPathInBuild treats flat data/* files as Chicago's.

Shared resources on the server

  • Basemap: the server build uses one regional Protomaps extract covering Chicago, Detroit and Dayton, so tiles shared between cities are stored once. The tablet build uses a per-city clipped extract. This needs either a basemapPmtiles override per build, or a shared basemap in the pack manifest. That is an interface change, so it goes to the Detroit plan's owner rather than being edited here. Measure the regional extract size before choosing; it is unmeasured.
  • Code: MapLibre, React, and the shared controls download once, because all profiles live in one bundle.
  • Backend: one lookup/map server and one cache (owner-lookup SQLite) serve every city.

9Deployment

Private server (all cities)

This builds on the Chicago session's in-progress no-Docker single server: phone_app.py becomes the map server. The server runs that app behind Caddy, which provides automatic TLS, serves static files, and supports HTTP Range requests for PMTiles. Access is controlled by one of:

  • Tailscale, free for personal use and recommended: nothing is exposed to the internet.
  • Caddy basic auth over TLS: reachable from anywhere, so §27 applies in full.

The PostGIS and Martin Docker stack stays a dev-machine tool for imports. The plan's §7 compares this with the full Docker stack and with the existing DreamHost static target.

Tablet (one city)

Run VITE_CITIES=dayton npm run build:static. The output is installed as a PWA from the private server. A "Download Dayton for offline" action stores the pack in Cache Storage, and the service worker answers PMTiles Range requests from the cache. The fallback is a Capacitor wrapper around the same build:

  • Android: free to sideload.
  • iOS: needs a paid Apple developer account for installs that last more than 7 days (cost flagged in plan §7).

Size budget: ≤ 120 MB per city, with buildings ≤ 70 MB.

12Testing

  • Acceptance gates: each it.todo or skipped test names its phase. A phase is done when its tests are real and passing.
  • Importers: recorded fixtures (one page of each ArcGIS layer saved as JSON), with no live network in CI.
  • Snapshots: the Chicago and Detroit layer lists stay byte-identical (createDefaultLayers.test.ts, added by the Detroit session).
  • Pack builds: CI builds VITE_CITIES=dayton and checks that dist has no chicago/detroit chunk or data folder, and that the total is ≤ 120 MB.
  • E2E: Playwright opens ?city=dayton, toggles each layer, clicks a building, and checks the popup shows Montgomery County data.
  • Coverage: 90% line coverage on the new modules (§22).

13Security

  • XSS: the fork's building popup interpolates tile properties into HTML unescaped. Dayton popups must use the shared escape helper. A test checks this.
  • ArcGIS where injection: the owner lookup normalises and quote-escapes addresses, the same way as soqlString.
  • Internet-facing server (§27):
    • TLS through Caddy.
    • Auth on every path, including PMTiles: the owner and appraisal data is public record, but compiled it is still sensitive.
    • Restrictive CORS and rate limits on the lookup endpoints.
    • Security headers.
    • No API keys in the client bundle; Google, Foursquare and Tracerfy stay server-side.
    Tailscale-only access removes public exposure entirely.
  • Tablet: offline packs contain owner names and mailing addresses. Rely on device encryption and a screen lock, and leave contacts out of tablet packs by default (an ADJUSTABLE build flag).
  • Supply chain: check every new npm or pip package on its registry before adding it (§8.5).
