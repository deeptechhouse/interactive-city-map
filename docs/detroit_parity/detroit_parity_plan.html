4Goal

A user who opens ?city=detroit in static mode (./start_map.sh) or dev mode gets the same experience a Chicago user gets:

  • Every Chicago layer has a Detroit counterpart with real data, or is deliberately not offered.
  • Detroit layers are clickable.
  • Filters speak Detroit's vocabulary (zoning codes, carriers, DDOT, SMART, QLine, People Mover).
  • Focus areas, contact list, owner batch and CSV work with Michigan addresses.
  • No Chicago behaviour changes. Chicago's layer list, importer plan and tests are pinned before any shared file is touched.

Done means: every un-skipped test in backend/tests/test_detroit_parity.py and frontend/src/cities/detroit/__tests__/ passes; all Chicago tests still pass; the feature matrix has no red rows except deliberate n/a; ≥90% line coverage on new modules.

5Approach

Architecture: city profiles. Replace scattered if (city === 'chicago') branches with a CityProfile port (frontend) and an importer registry (backend). Detroit becomes new files that plug into these seams. Shared code asks the profile, never "which city is this?". Detail: TDD §3.

Paradigm, per layer (§5):

  • Backend importers: OOP. Template method on BaseImporter. Detroit importers subclass the shared ones and override only transform() (Open/Closed: Chicago importers stay untouched). Field names are data in field_maps.py.
  • Post-import enrichment: procedural SQL. Set-based UPDATE … FROM spatial joins in functions. No classes for their own sake.
  • Frontend: functional / hook-based. A profile is a plain typed object. Contact sources are classes because they implement the existing OwnerSource/BusinessSource ports.
  • Static export: a script, procedural, shelling out to GDAL/tippecanoe/pmtiles.

Chicago isolation rule. Every shared-file edit happens at a single "seam" and is preceded by a snapshot test of Chicago's current output. Examples of seams: run.py calls importers_for(); useMapLayers calls getCityProfile(); buildZoningFilter gains an optional classes argument. Detroit-specific logic never lives in a shared file.

6Steps

Each phase lists its dependencies, then the steps. "Seam" marks a step that edits a shared file. Each phase ends with an acceptance gate.

P0 — Safety net (no deps · ½ day)

  1. Commit or branch the existing uncommitted work first. The working tree has 41 modified and ~50 untracked files on master. Detroit seams will touch some of the same files. Put Detroit work on feat/detroit-parity.
  2. Snapshot tests that pin Chicago:
    • createDefaultLayers('chicago') output
    • run.py importer order for Chicago
    • buildZoningFilter output for a fixed active set
    • ContactResolver Chicago wiring
  3. Fix the venv: install httpx into backend/.venv, and get ruff past the macOS Gatekeeper block (see Risks).

Gate: Chicago snapshot tests are green on the branch.

P1 — Schema (P0 · ½ day)

  1. Pre-flight: run \d zip_codes and \d major_streets on the Chicago DB, then reconcile them with the skeleton models.
  2. Move alembic/drafts/005_city_parity_tables.py into versions/ and implement it. The six tables are council_districts, police_precincts, zip_codes*, major_streets*, parks and business_licenses. The two tables marked * use IF NOT EXISTS/ALTER and never DROP.
  3. Import the six skeleton models in models/__init__.py (seam).

Gate: alembic upgrade head then downgrade -1 then upgrade leaves the Chicago rows in zip_codes/major_streets intact; test_models passes.

P2 — Backend import pipeline (P1 · 4–5 days)

  1. Verify field names live. GET ?f=json on each Detroit layer, correct field_maps.py, and set verified=True with the date. This includes checking whether SEMCOG supports f=geojson.
  2. Implement city_registry.importers_for(), then switch run.py to use it (seam). Chicago's plan excludes blight, DLBA and neighborhoods. This closes the high-severity blight defect.
  3. Move the blight URLs from import_blight.py into detroit.yaml and add the geolocated-only where clause, so it no longer downloads all 874K tickets.
  4. Implement the Detroit importers in dependency order:
    1. parcels
    2. buildings (split multipart, clip to city limit)
    3. zoning
    4. boundaries
    5. parks
    6. business licences
    7. major streets
    8. waterways (field-map override)
    9. railroad RoW
    Transit, railroads, POIs, neighborhoods, DLBA and blight run as they are.
  5. Implement detroit/enrich.py (zoning, parcel, POI and licence joins, all filtered by city_id).
  6. Run python -m app.data_import.run --city detroit. Record row counts in error_log.html and sanity-check against the expected volumes (~300K buildings, ~378K parcels, 12 precincts, 7 districts, 205 neighborhoods).

Gate: the Phase-2 tests in test_detroit_parity.py are un-skipped and green; Chicago row counts are unchanged after a Detroit run.

P3 — Static assets (P2 · 1–2 days)

Gate: public/data/detroit/ exists, every PMTiles header's bounds fall inside Detroit's bbox, and no file under public/data/ outside detroit/ has changed.

P7 — Sanborn for Detroit (P3 · 3–5 days, mostly georeferencing)

  3. Give SanbornOverlay its sheet list from the profile. Until then, Detroit's Sanborn layer is hidden, not shown with Chicago sheets (do this in P4).

  4. Run OSM indoor and the venue scraper with --city-id for the Detroit POI categories, then compute IBC occupancy estimates as Chicago does.

9Licensing & costs

Licensing posture is the same as Chicago (you confirmed this). All Detroit data sources are free public open data: the City of Detroit ArcGIS Hub, SEMCOG, Data Driven Detroit, USGS NHD, Census TIGER, the DDOT/SMART/QLine/DPM GTFS feeds, OSM (ODbL; attribution is required and already shown), and Library of Congress Sanborn maps (public domain). The new tooling (tippecanoe, GDAL, pmtiles) is open source. No new paid services.

The existing paid services are Google Places, Foursquare and Tracerfy. Detroit adds usage, not new contracts. Tracerfy charges per hit (1 credit per name trace, 2 per address trace), so fixing the Chicago/IL hard-coding before any Detroit batch is run avoids spending credits on wrong-city lookups.

10Risks & open questions

  • Uncommitted work on master. The 41 modified and ~50 untracked files include the Chicago contacts, focus and presets work. Seam edits in P4–P6 touch the same files. Commit or branch it before P4.
  • Unverified Detroit field names (every field_maps.py entry), the SEMCOG output format, whether the zip layer has geometry, and the stale permits URL. P2.1 resolves all of these before any importer logic is written.
  • CORS on the City of Detroit ArcGIS services is not yet tested. A phone_app.py proxy is the fallback.
  • Tooling: macOS Gatekeeper blocked backend/.venv/bin/ruff ("Screen Sharing created this file"), and backend/.venv lacks httpx. Reinstall ruff with pip3 install --force-reinstall ruff==0.6.9 inside the venv, or allow it in System Settings → Privacy & Security.
  • Data volume: parcels (~190 pages) and blight (if left unfiltered) are large. Cache downloads and never re-download because of a transform bug.
