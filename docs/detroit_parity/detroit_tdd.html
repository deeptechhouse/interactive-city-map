1Scope

In scope: bring Detroit to Chicago's feature level in both run modes (static and dev), and introduce a city-profile seam so the work goes into new files instead of edits to Chicago code.

Out of scope: new features Chicago doesn't have; Dayton and Cincinnati (although the seam makes them cheap); the interior editor and ML work listed in the earlier interior roadmap.

Non-negotiable constraint: Chicago's output stays identical. Every shared-file change is a seam pinned by a snapshot test taken beforehand.

2Current state (summary)

Detroit has a config (detroit.yaml, 16 sources), three Detroit-only tables, importers and layers (neighborhoods, DLBA, blight), and a GTFS transit path. It has no imported data, no static assets, and no Detroit-aware vocabularies, popups, focus areas or contacts. Several shared paths leak Chicago data into Detroit. The full matrix and defect list are in the plan §2–3.

3Architecture

Orange outline = new seam. Arrows show the direction of calls and data. Static mode reads public/data/<slug>/ directly; dev mode reads Martin.

Design principles applied

  • Open/Closed: a city is added as new profile and importer files. Shared code is extended through ports, never by adding a city branch.
  • Dependency inversion: shared consumers depend on CityProfile, OwnerSource/BusinessSource and BaseImporter, never on a concrete city.
  • Fail closed: an unknown slug returns null, not Chicago. A feature a city lacks (focus: null, contacts: null) shows a "not available" note instead of another city's data.
  • Single source of truth: upstream field names live in field_maps.py, and generated vocabularies (POI counts, GTFS colours) come from the exporter, never hand-typed.

4Data model

All tables use id uuid PK, city_id → cities.id, geom in SRID 4326, metadata JSONB, a GIST index on geom and a btree index on city_id. Migration 005 is drafted at backend/alembic/drafts/005_city_parity_tables.py.

5.3 City switch lifecycle

The current code only ever adds layers. The new flow: prevProfile.layers() → removeCityLayers(map, ids), which removes the style layers and then their sources. Then the new profile's basemap and layers are added, and visibility is re-synced. POIBrowsePanel adds citySlug to its effect deps.

5.4 Focus areas

Detroit reuses the three FocusKind slots: zip → ZCTA, police → DPD precinct, ward → council district (labelled "Council districts"). Boundaries are bundled TS loaded with dynamic import(), so Chicago users never download them. focusGeometry.ts is unchanged.

5.5 Zoning

DETROIT_ZONE_CLASSES uses the same ZoneClass/ZoneType shape. buildZoningFilter(active, classes = ZONE_CLASSES) keeps Chicago's catalogue as the default. The Detroit catalogue is filled from the distinct imported codes, not from memory: expected R1–R6, B1–B6, M1–M5, W1, TM, PD, PC, PCA, PR, P1, SD1–SD5, MKT (unverified). Class keys must equal what the backend's DetroitZoningImporter emits.

Flow: run.py --city detroit → _ensure_city_record → importers_for('detroit') → each Importer(db_url, city_id, cfg).run() (download → transform → load) → detroit.enrich.run_all().

Chicago's plan is today's order minus neighborhoods, DLBA and blight. A snapshot test pins it.

Idempotency: each load() deletes that city's rows for its table before inserting, so a re-run never duplicates rows and never touches another city's.

Complexity: enrichment uses GIST-indexed joins, O(n log m) in the database, with no Python nested loops (§41).

9Deployment

  • Static mode (primary): export_city_static.py --city detroit writes frontend/public/data/detroit/ and src/cities/detroit/data/. ./start_map.sh and build:static need no changes. Chicago's existing un-prefixed files stay; moving them is a separate optional PR.
  • Dev mode: docker compose up -d → alembic upgrade head → python -m app.data_import.run --city detroit. Martin picks up the new tables automatically.
  • Size budget: Detroit's total static assets should stay under ~120 MB (buildings ≤ 70 MB). Users download only their city's files.

11Testing strategy

  • Chicago pins (P0): snapshots of the layer list, the importer plan, the zoning filter and the contact wiring. Any diff fails the build.
  • Unit:
    • field-map pick()
    • Detroit zoning classifier
    • multipart split
    • owner/licence adapters (with an injected FetchJson)
    • popup escaping
  • Integration: run the importers against recorded ArcGIS fixtures (no live network in CI). Enrichment runs against a two-city test DB and asserts Chicago rows are untouched.
  • E2E (Playwright): Detroit static mode loads with a basemap; switching Chicago → Detroit → Chicago leaves no stray layers; a building click opens the detail panel; the contact list resolves a known Detroit address (mocked).
  • Coverage: ≥90% lines on new modules (§22). Ask before merging to main whether to target 98%.

12Security

  • Query injection: addresses taken from tiles go into ArcGIS where clauses. Reuse normaliseAddress (allow-listed characters) and quote doubling, and never pass raw tile properties into a query.
  • XSS: all popup values are open data, so treat them as untrusted and HTML-escape them in the Detroit popup builders.
  • Paid-API spend: the hard-coded Chicago/IL owner batch was a credit-wasting defect. Validate city/state in BatchItem (2-letter state, bounded length). The existing per-IP rate limits apply.
  • Secrets: no new keys. The Detroit open-data endpoints are keyless, and the Google, Foursquare and Tracerfy keys stay server-side.
  • Internet-facing (§27): no new public endpoints. The BatchItem change sits behind the existing local-only and rate-limited routes.
