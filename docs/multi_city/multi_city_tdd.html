1Why combine, and what this document is

Most of the Detroit plan is shared infrastructure:

  • schema
  • the importer registry
  • the static exporter
  • the profile registry
  • city-switch cleanup
  • vocabulary and focus seams
  • contact seams

Dayton needs the same infrastructure, so planning them separately would schedule and test it twice. This document merges the two:

  • Shared work S is designed and built once, in waves.
  • City work (Detroit, Dayton) runs in parallel lanes inside each wave. Each city owns its own directories, so the lanes never edit the same file.
  • Chicago work C belongs to the Chicago session, and it gates every wave (§2).

The four per-city documents stay as detailed references. Section numbers below point into them, for example "D-TDD §5.6" or "Y-TDD §8". Where they disagreed, §11 records the resolution, and this document wins.

2Chicago safety: the non-negotiable rules

Chicago is in use for research today. Until the Chicago session says otherwise, no multi-city work touches master, the master working tree, Chicago's static assets in frontend/public/data/, or a running ./start_map.sh. All Detroit and Dayton work happens on branches in separate worktrees.
  1. Branches, not master. Multi-city work lands on feat/multi-city (§8). It reaches master only at a merge point the user chooses, never on a research day, and only with every gate green.
  2. Pin before you touch. Before any shared file changes, a snapshot test pins Chicago's current output. The first pin already exists: createDefaultLayers.test.ts, Chicago's 15 layers. Wave 0 adds the rest:
    • importer order
    • buildZoningFilter output
    • ContactResolver wiring
    • the basemap URL
    • getLayerSourceUrl for every Chicago layer
    A diff in any pin fails the wave.
  3. One seam per shared file. City logic never goes into shared code. A shared file changes in exactly one place, where it starts asking the profile.
  4. Defaults are Chicago. Every new shared parameter defaults to today's Chicago value. Examples: buildZoningFilter(active, classes = ZONE_CLASSES), and BatchItem.city = "Chicago".
  5. Chicago assets stay put. Moving public/data/*.pmtiles into public/data/chicago/ is the last, optional step (Wave 9). The Dayton pack filter treats flat files as Chicago's until then.
  6. Chicago-session files. Shared seams in MapContainer.tsx, contacts/**, routes/contacts.py, api/*.ts and phone_app.py are handed to the Chicago session as written specs, such as D-TDD §13 F-1 and F-2. This plan does not edit them directly.
  7. Manual smoke test per wave. Run ./start_map.sh on the branch worktree, on a different port: Chicago loads, layers toggle, a building popup opens, the contact list resolves one known address, and a saved search applies.

  • Ports, frozen in Wave 4:
    • CityProfile, quoted verbatim in D-TDD §5.1, plus the accepted optional build-level basemapPmtiles (D-TDD §13.4).
    • OwnerSource / BusinessSource.
    • BaseImporter.
    • FieldMap, moving to the shared app/data_import/field_map.py.
  • Paradigm per layer, the same for both cities:
    • Importers are OOP: template-method subclasses that override transform().
    • Enrichment is procedural, set-based SQL.
    • Profiles are data-shaped modules. Contact sources are classes, because they implement the existing ports.
    • The exporter and the Vite plugin are procedural scripts.
  • Fail closed: an unknown slug returns null, and an unknown VITE_CITIES value fails the build. focus / contacts set to null means "not available here", never another city's data.
  • Modularity: city packs (Y-TDD §8). The default build includes every city. VITE_CITIES=dayton builds a one-city tablet bundle.

Critical path and parallelism

  • Critical path: W0 → W1 → W2 → W3 → W4 → W5/W6 → W9. W7 can start after W4, and W8 after W3.
  • No shared seam needed: the city-lane work in W1 (source verification) and the importer bodies in W2 only touch city folders and can run against fixtures. Both can start now, on the branch, with zero risk to Chicago.
  • Efficiency compared with two separate plans: roughly 8–10 days of seam work is done once instead of twice. One set of Chicago pins guards both cities. Each wave gets one review. Fixtures and the field-map method are shared.

9Testing

  • Chicago pins (W0) as described in §2. They run first in every CI job, and any diff blocks the merge.
  • City acceptance suites: test_detroit_parity.py plus detroitProfile.test.ts, and test_dayton_parity.py plus daytonProfile.test.ts. Each todo or skip names its old phase, and its wave is in §7.
  • Cross-city tests, added once:
    • Enrichment on a three-city test database touches only its own city's rows.
    • Switching Chicago → Detroit → Dayton → Chicago leaves no stray layers or sources.
    • An unknown slug returns null.
    • A pack build contains no other city's code or data.
  • Fixtures: recorded ArcGIS and GTFS pages per city. CI never calls live services.
  • E2E (Playwright): each city loads in static mode, a building click opens the detail panel, and the contact list resolves (mocked).
  • Coverage: ≥90% lines on new modules (§22). Ask about 98% before the W9 merge.

10Security (both cities)

  • XSS: every popup HTML-escapes tile properties. The old Dayton fork's popup did not, so don't port it as-is.
  • ArcGIS where injection: run addresses through normaliseAddress and double the quotes, for both cities' owner sources.
  • Paid-API spend: F-1 ships before any Detroit or Dayton owner batch can run. City and state are validated.
  • Secrets: none new. Every new source is keyless. Google, Foursquare and Tracerfy keys stay server-side.
  • Hosting (W7, §27): TLS through Caddy, Tailscale-only access recommended, auth on every path including PMTiles, rate limits, security headers.
  • Tablet packs: contacts stay out of tablet builds by default. Rely on device encryption.

12Risks

  • Chicago regression on a research day. Mitigation: the §2 rules. Nothing reaches master until W9, and the user picks the merge day.
  • Snapshot drift. feat/multi-city-wip froze master's working tree on 2026-10-02, and the Detroit and Chicago sessions have edited master since (arcgis_helper paging, blight, useMapLayers B-4/B-5, docs). W0 replaces the snapshot with a real commit. Rebasing the Dayton files is conflict-free, because they are all new.
  • Seam owner bandwidth. Both lanes block on W1–W4 shared steps. Mitigation: the city lanes do their seam-free work first (W1 verification, W2 importer bodies against fixtures).
  • Unverified upstream fields in both cities' field maps. W1 resolves them before any importer logic is written.
  • Lost Dayton enrichment. The W0 pg_dump comes first.
  • Tooling: the backend venv lacks pytest and httpx, ruff is blocked by Gatekeeper, and pyproj doesn't build on this macOS. W0 fixes the venv. Until then, use a scratch venv.
